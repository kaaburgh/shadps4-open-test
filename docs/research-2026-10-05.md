## Executive decision

The first workload is `gpu_solid_rt`.

It renders an oversized fullscreen triangle into a 64x64
`R8G8B8A8_UNORM / DISPLAY_LINEAR_ALIGNED` offscreen color target. Both vertex and pixel
shaders are authored in this repository and compiled to SPIR-V and then PS4/GFX7 shader
binaries. The fragment shader writes exact opaque white.

The guest pre-fills the render target with zeroes, submits the draw, waits for an EOP event
that flushes color-buffer data, then checks sixteen interior pixels. Every sampled pixel must
be exactly `0xffffffff`.

This was chosen instead of the upstream OpenGNM hardware smoke test because that smoke test's
visible status framebuffer is written by the CPU; its GNM command stream uses a zero-count draw
plus EOP. It is useful for submit/EOP validation, but does not prove rasterization or shader
translation.

This was also chosen instead of the upstream `freegnm-examples` triangle as-is because the
stage-0 test should have a machine-readable oracle and no dependency on VideoOut or the legacy
freegnm compatibility headers.

## Important oracle caveat: readback is part of the test

Current shadPS4 defaults are:

- `readbacksMode = Disabled`;
- `readbackLinearImages = false`.

Its texture cache marks render targets GPU-modified and only schedules automatic downloads of
linear images when `readbackLinearImages` is enabled. Therefore a guest CPU pixel read is not
a neutral renderer-only oracle under default settings.

The host runner deliberately creates an isolated `XDG_DATA_HOME` and writes:

```toml
[GPU]
readbacksMode = 2
readbackLinearImages = true
```

for this stage-0 test. That makes the requirement explicit and reproducible.

Consequences:

- `gpu_solid_rt` currently validates a combined path: shader/raster/render-target correctness
  plus the configured GPU-to-CPU linear-image readback path.
- A failure must not automatically be diagnosed as a shader/raster failure.
- A later `triangle_present`/VideoOut test with host screenshot capture should provide an
  independent presentation/raster oracle.
- A later dedicated coherence/readback test should isolate GPU->CPU visibility.

For a first end-to-end test this coupling is acceptable because it gives a very strong,
machine-readable oracle with almost no image-comparison machinery. It is explicitly documented
rather than hidden.

## OpenOrbis status

Current OpenOrbis is suitable for the guest compiler/sysroot side without an official Sony SDK.

The latest release observed during research is `v0.5.4`, published in January 2026. The
release provides `toolchain-llvm-18.tar.gz`; the SHA-256 recorded in `deps.lock` is the
release-provided checksum.

The toolchain project is GPL-3.0. Its homebrew samples link against its open runtime/toolchain
pieces and generated import stubs.

The commonly seen package files `sce_module/libc.prx` and
`sce_module/libSceFios2.prx` are not evidence that an official Sony SDK is required:
current OpenOrbis source contains modules for both and its changelog describes them as
stub/empty modules. They can be built by OpenOrbis itself.

Stage 0 does not package a PKG at all, so those modules and package metadata are unnecessary.

## OpenGNM status

Current OpenGNM is a clean/open GNM implementation and is explicitly OpenOrbis-compatible.
Its current OpenOrbis build flow is:

```bash
export OO_PS4_TOOLCHAIN=/path/to/openorbis
cp config.orbis.mak config.mak
make lib
```

A guest target links the OpenGNM archive and imports the normal PS4 HLE-facing libraries,
principally `libkernel` and `libSceGnmDriver`.

For shadPS4 raw-ELF execution these are resolved by shadPS4's HLE; no Sony PRX needs to be
copied beside the ELF.

OpenGNM currently exposes the pieces stage 0 needs:

- linear color render target creation and byte-size calculation;
- GNM draw command construction;
- VS/PS register structures and shader binary format;
- command-buffer submission;
- EOP events and color-buffer flush event types.

OpenGNM is MIT licensed.

## Shader compiler status

`opengnm-psbc` converts SPIR-V to PS4 shader binaries using the vendored Mesa NIR/ACO path.
PS4/Liverpool output must be selected explicitly with `-4`; its default target is not the PS4
GFX7 target.

The repository currently has a reproducibility rough edge: its Makefile defaults to
`config.mak`, but a generic Linux `config.mak` is not tracked. It also expects sibling
`SPIRV-Headers` and `Vulkan-Headers` trees for generated-source inputs/includes.

This repository therefore supplies a small host Linux config in
`tooling/opengnm-psbc-linux.mak` and pins those header repositories. This bootstrap path has
been implemented but has not yet been validated by a full build in this ChatGPT run.

## Raw ELF in current shadPS4

Current shadPS4 CLI accepts a PS4 ELF path directly. In the direct-ELF path it mounts the
executable's parent directory as `/app0`.

That gives the stage-0 output this layout:

```text
out/gpu_solid_rt/
├── gpu_solid_rt.elf
└── assets/
    ├── fullscreen.vert.sb
    └── solid.frag.sb
```

and lets the guest load its generated shaders from `/app0/assets/...`.

The raw ELF path is the preferred test format because it removes package construction,
metadata, install steps and package-only support modules. It is not dependent on extracted
commercial files.

## Current shadPS4 native tests

shadPS4 already has native host-side tests built with GoogleTest, including GCN-related tests.
Those are complementary to this repository: they are better for narrow C++/shader-recompiler
unit behavior, while this project exercises the guest ABI/HLE/GNM path end to end.

No current maintained public suite equivalent to a broad OpenOrbis/OpenGNM guest conformance
suite was found in the repositories/searches reviewed for this stage.

Useful upstream ingredients do exist:

- OpenOrbis samples for libkernel/threading/input/networking/graphics;
- OpenGNM host tests and hardware smoke;
- `freegnm-examples` workloads such as triangle, cube, shader tests, indirect draw,
  instancing, primitives, linear VideoOut and DMA/blit.

The intended strategy is reuse/reduce those ideas, not invent a large framework first.

## Headless/cloud status

Current shadPS4 contains an internal headless window-system concept in renderer code, but the
current CLI does not expose a practical `--headless` guest-run path.

The SDL frontend still initializes the video subsystem/window. A current upstream issue from
2026-10-04 demonstrates a synthetic ELF progressing through loader setup on a displayless
Linux host and then failing at SDL video initialization with `No available video device`.

Therefore the honest stage-0 cloud status is:

- GPU compute/rendering on a Vast machine is technically plausible;
- current upstream shadPS4 is **not turnkey displayless**;
- the provided runner requires `DISPLAY` or `WAYLAND_DISPLAY` unless explicitly overridden;
- Xvfb/virtual-Wayland/gamescope workarounds are not declared supported here until measured;
- the clean long-term solution is likely a small shadPS4 CLI/frontend headless path using its
  existing renderer-side headless plumbing.

This is the largest remaining infrastructure blocker for a completely unattended fresh Vast VM.

## PASS/FAIL contract

Guest:

```text
SHADTEST name=gpu_solid_rt status=PASS samples=16 expected=ffffffff ...
SHADTEST name=gpu_solid_rt status=FAIL reason=... ...
```

The guest writes the marker to normal output and the kernel debug-output path.

Host:

- scans combined shadPS4 stdout/stderr for the marker;
- saves `out/<test>/run.log`;
- exits 0 for PASS, 1 for guest FAIL, 2 for infrastructure/no-marker failure;
- terminates shadPS4 after receiving the oracle if the frontend remains alive.

shadPS4's own process exit code is deliberately not the guest oracle: current CLI returns from
the emulator frontend independently of the test's semantic result.

## Determinism

For stage 0, exact pixel equality is intentionally stronger and simpler than screenshot hashing:

- RGBA8 UNORM target;
- only all-zero prefill and all-one shader output;
- no texture filtering;
- no blending;
- no interpolation-dependent color;
- samples are away from triangle edges;
- pitch is queried from the render target.

If this exact test passes on multiple Vulkan vendors, its oracle should remain exact.

For future tests involving interpolation, filtering, floating point, derivatives, MSAA or
vendor-sensitive raster details, exact full-image hashes are likely too brittle. Prefer one of:

1. exact checks on deliberately exact pixels/integers;
2. per-pixel tolerances;
3. small semantic probes;
4. diagnostic screenshots in addition to the machine oracle.

## OpenGNM coverage limits

Passing an OpenGNM workload does not prove full commercial-game GNM compatibility.

Important blind spots include:

- undocumented or not-yet-implemented GNM entry points;
- direct/raw PM4 patterns a commercial title may emit;
- SDK-generated command sequences that OpenGNM does not reproduce byte-for-byte;
- proprietary Sony shader-compiler output patterns that differ from Mesa/ACO-generated psbc
  output;
- unusual resource layouts, metadata/compression paths and synchronization patterns not
  represented by a synthetic test;
- game-specific CPU/GPU shared-memory behavior.

This is why the desired workflow is reduction: observe a bug in a commercial game, minimize it
into an open guest reproducer where possible, then keep the open reproducer as the regression
test.

## Licenses and artifact policy

Observed project licenses:

- OpenOrbis toolchain: GPL-3.0 project;
- OpenGNM: MIT;
- opengnm-psbc: MIT project with vendored Mesa-derived source under its upstream permissive
  licenses;
- freegnm-examples: MIT;
- SPIRV-Headers: Khronos permissive/MIT-style license;
- Vulkan-Headers: Apache-2.0.

Repository-authored code is MIT.

Recommended artifact policy for now:

- commit source, scripts, lock file and expected semantic results;
- build `.spv`, `.sb` and guest ELF reproducibly;
- do not commit extracted Sony modules or any commercial assets;
- generated `.spv`/`.sb` from shaders authored here are reasonable redistributable
  artifacts, but source remains canonical;
- defer committing prebuilt ELF until the licenses/notices of every statically linked OpenOrbis
  runtime object have been audited once. There is no technical need to store the ELF in git.

That last point is conservative license hygiene, not evidence that the ELF contains Sony code.

## Fresh Ubuntu/Vast workflow

Host packages for the test-suite side are expected to include at least:

```bash
sudo apt update
sudo apt install -y git curl ca-certificates make clang lld llvm glslc \
    python3 python3-mako
```

Then:

```bash
git clone https://github.com/kaaburgh/shadps4-open-test.git
cd shadps4-open-test

bash scripts/bootstrap-deps.sh
bash scripts/build-test.sh gpu_solid_rt
```

Current upstream shadPS4 recommends Clang 19 on Ubuntu 24.04. Its documented build is:

```bash
git clone --recursive https://github.com/shadps4-emu/shadPS4.git
cd shadPS4
cmake -S . -B build/ -DCMAKE_C_COMPILER=clang-19 -DCMAKE_CXX_COMPILER=clang++-19
cmake --build ./build --parallel"$(nproc)"
```

With a usable Vulkan display session:

```bash
cd /path/to/shadps4-open-test
SHADPS4=/path/to/shadPS4/build/shadps4 \
    bash scripts/run-test.sh gpu_solid_rt
```

The runner uses an isolated shadPS4 config for the stage-0 readback oracle.

## What is implemented vs still unproven

Implemented in this repository:

- pinned dependency set;
- OpenOrbis release bootstrap;
- OpenGNM source build;
- Linux host config/build path for opengnm-psbc;
- source shaders;
- offscreen GNM guest test;
- raw-ELF output layout;
- host marker parser;
- isolated shadPS4 readback config;
- explicit displayless failure message.

Still unproven in this ChatGPT run:

- a full bootstrap build on a clean Ubuntu machine;
- successful psbc host compilation with the supplied generic config;
- successful PS4 ELF link;
- successful shadPS4 launch;
- exact `0xffffffff` CPU-visible readback on current shadPS4;
- behavior across AMD/NVIDIA Vulkan drivers;
- a practical Vast display/headless setup.

The next meaningful action is empirical, not more architecture: run the exact three commands on
one Linux GPU host, fix only the concrete build/runtime failures, and preserve the first known
PASS log as the baseline.
